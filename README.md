# Mittes 的一天 (A Day With Mittes)

给 Mittes 一份会自己长出来的日程，并让它以正确的方式影响她说话。

MaiBot 插件，**主程序改动 0**。当前 v3.1.5。

---

## 为什么这样设计

旧版把日程做成一句话查表，一旦进了上下文，Mittes 就会反复提及——"我现在正在洗碗呢，有什么事情吗？"
在 prompt 里写"不要提及"没用，那是在跟注意力机制对着干。

根因不在"注入还是工具"，而在于传的是**事实**还是**风格**：

| | 内容 | 出现时机 | 是否含活动名词 |
|---|---|---|---|
| **事实层** | 她具体在做什么（故事化文本） | 只有被问才出现（Tool） | 有，这是它的价值 |
| **状态层** | 她的身体/情绪，以及这如何影响说话 | 每轮都在（常驻注入） | **绝对没有** |
| **谈资层** | 这段时间里值得说给人听的那一件事 | 常驻注入，**说出口后立刻撤掉** | 有——唯一的例外 |

「正在洗碗」是一句可陈述的事实，模型有复述冲动；「你有点累、话短」不是可陈述内容，
模型没法复述它，只能照做。**状态层的不可复述性完全建立在「没有活动名词」这条纪律上。**

谈资层是有意开的口子：事实层有个先天缺陷——几乎没人会主动问「你在干嘛」，工具不被调用，
story 就永远用不上。它的止损方式不同：**说完就从上下文里消失**，一件事只说一次。

> **绝不能改成注入「这件事已经说过了，不要再提」。** 要否定一件事，你必须先把它写进上下文；
> 注意力对「伞的事」的反应远强于对「别提」的。不可复述只能靠「上下文里根本没有」。

完整设计见工作区里的 `a_day_with_mittes-重构设计.md`（**不在本仓库内**）。

## 写 prompt 的两条原则

这是这个插件最贵的一部分知识，全都是踩出来的，别的项目也用得上。

### 原则一：规则只能「排除」，不能「示范」

**禁令**排除掉一部分输出，剩下的仍然是无限的——「不要写重大事件」之后，小事还有无穷种写法。
**示范**（列一串题材、给几个措辞、配一个完整例句）会让模型在示范附近采样，创作自由度当场坍缩。

| 踩的坑 | prompt 里写了什么 | 后果 |
|---|---|---|
| 负面事件只有那十几种 | 配置里手写事件池 | 设计阶段就被否掉 |
| 20 段里 13 段同一个开头 | 给「首句要出现 Mittes」配了完整例句 | 同一个句子滚了两天 |
| story 题材趋同 | 「打翻一杯水、找不到发圈、被熟客认出来……」 | 20 段里命中 5 段 |
| mood 措辞趋同 | 「踏实 / 懒洋洋 / 心里冒泡 / 跃跃欲试 / 被逗乐」 | 20 段命中 9 段，其中一条被**逐字**照抄 |
| 十段 story 读起来一个味 | 唯一那个正例 | 题材零照抄，但**文体 10/10** |

**「安全的正例」很可能根本不存在。** 曾经以为「示范结构判据的对照例是安全的」，
证据是那个正例"20 段零照抄"——但那个统计只看了题材。一个完整例句同时携带三层：

| 层 | 被复制了吗 |
|---|---|
| 题材 | 否，0/20 |
| 句式 | **是**，平均每句 2.8 个逗号 |
| 文体 | **是**，10 段里 0 处直接引语、7 段以抒情句收尾 |

文体最难察觉，因为它不像题材那样显眼——它看起来只是"写得好"。

落笔时：**反例可以留，正例要吝啬**；**不列题材清单**，正向反向都不行
（反向清单会替模型做完判断，实测把「画油画」「涂指甲油」这些很有得讲的段落顺手扫掉了）。

### 原则二：只写模型不可能知道的信息，不写它本来就会的能力

发现原则一之后，story 规则一度变成这样——全是禁令，符合原则一，但**依然是错的**：

```
- 长短句交错。一整段用逗号把动作串下来，读的人喘不过气
- 有人说话就写成引号里的原话，不要一律转成「说是……」
- 别每段都收在一句总结性的抒情上
```

一个称职的写手第一次读到「长短句交错」只会觉得莫名其妙。这类规则是写给"知道我踩过什么坑"的人看的，
是在**治症状**——真正的病因是「100~150 字 + 有起因有推进有转折」：130 字塞完整三幕，
只能靠逗号把动作串起来。**把字数放开、把任务说清楚，句法自己就顺了。**

| 留 —— 它不可能知道 | 删 —— 它本来就会 |
|---|---|
| 人称/格式契约（下游字段要对齐） | 长短句、对话怎么写、别都收在抒情上 |
| 字数预算 | 「有起因、有推进、有一点小转折」 |
| 外部事实（骨架的地点/服装/同处） | 「不是定格一帧画面」 |
| 跨调用状态（它看不到全局） | 「把它写成这段时间的主线」 |
| 常驻注入的禁名词纪律（设计地基） | |

按这把尺子，story 规则从 20 行降到 4 行。还要额外注意两类：

- **死规则**：manner 里曾有一条「不要写篇幅要求，那是另一个字段的事」，
  可那个字段早就整个取消了——它在跟模型解释一个不存在的东西。这类最容易残留，值得定期查。
- **执行不了的规则**：mood 里曾有「不要一整天都在同一个强度上」，
  可时段是**一段一次调用**，模型只看得到上一段，看不到"一整天"。改成它确实看得到的参照才有意义。

## 注册的组件

| 类型 | 名称 | 说明 |
|---|---|---|
| Tool | `get_current_schedule` | 事实层：返回当前时段的故事化文本，被问才吐 |
| Tool | `get_weather` | 查询指定城市的实时天气和近 3 天预报 |
| Hook | `maisaka.planner.before_request` | 在「时间：」那条 item 后插入状态层（忙碌度 / 心情） |
| Hook | `maisaka.replyer.before_model_request` | 在 `reply_reference` 之前插入说话方式（A）与谈资（C） |
| Hook | `maisaka.replyer.after_response` | `observe` 模式只读，检测谈资有没有被说出口 |
| Command | `/status *` | 调试命令，仅 operator |

**主程序改动：0。** 所有注入都走插件 hook，跟上游同步时零冲突。

### 主程序 API 上的两处硬依赖

这两处是直接 import 主程序内部模块的，不走 SDK，上游重构会打断，同步版本时要重点回归：

- `LLMServiceClient` + `LLMGenerationOptions`（`generator.py`）—— 为了**钉死具体模型**，见下文。
- schema v6 的推理记录格式（`preview.py`）—— 为了让调用出现在 WebUI，见「可观测性」。

### Command 的正则命名组不会拆成形参

主程序把 `(?P<day>…)` 整包塞进一个 `matched_groups` 字典，**不**拆成同名关键字参数。
写成 `async def cmd(self, day: str = "")` 不会报错，只是 `day` 永远是默认值——
`/status batch today` 因此一直生成的是次日。这类失效全程静默，只能静态查。
正确写法见 `plugin.py` 的 `_group(kwargs, name)`。

## 模型：必须指定模型名，不能只给任务名

`llm.generate` 这条 capability **只收任务名**（内部 `resolve_task_name`），而任务名只决定**候选池**：
`replyer` 的 `selection_strategy` 是 `random`，四个模型随机挑，sonnet 5 只有 1/4 的概率。
整套 prompt 的判据是照着强模型的水平定的，随机挑模型会让每天的质量方差**压过 prompt 本身的影响**。

所以绕开 capability，直接用 `LLMServiceClient(task_name=...)` + `LLMGenerationOptions(model_name=...)`，
任务名只当**基座**（借它的 `hard_timeout` 和统计管线），模型由 `model_name` 覆盖。

```toml
[generation]
model        = "claude-sonnet-5"   # 时段生成，填的是 [[models]].name
digest_model = "glm-5.2"           # 当日概要压缩
topic_model  = "glm-5.2"           # 话题提炼
base_task    = "memory"            # 基座：只借 hard_timeout（240s）
```

`base_task` 选 `memory` 是为了超时：`replyer` 只有 60 秒、`utils` 只有 **20 秒**，
而实测有过 36.9 秒的单段调用，话题提炼更是一次吞十段 story。

### 推理和正文共用 max_tokens

`_MAX_TOKENS = 32000`，给得很宽是有原因的：推理模型的 reasoning 和正文**共用这一个预算**。
实测 glm-5.2 跑全天话题提炼时把 4000 token 全烧在 reasoning 上，一个字正文都没吐出来，
而 `status` 仍是 `completed`，主程序不当失败。所以空响应现在区分两种成因：
「被 max_tokens 截断（N/32000 全部用于推理）」和「真的空」。

## 数据

### 骨架 `schedule_skeleton.toml`（手写，纳入版本库）

7 天 × 10 段变长时段，每段七个字段：

```toml
[[schedule_mon]]
start   = "18:00"
end     = "21:00"
title   = "晚班营业"
place   = "店里营业区"          # 素材支点
outfit  = "猫耳女仆装"          # 素材支点
company = "客人、店长"          # 素材支点
kind    = "工作"                # 唯一一个机器要读的字段
```

划界原则：**骨架放「客观且不该每天变的事实」，LLM 写「这些事实今天具体表现成什么样」。**

同一份文件里的 `[fallback."<kind>"]` 是底稿——冷启动、生成失败、缓存缺失时顶上的默认状态。

> TOML 的裸键不允许非 ASCII，中文 `kind` 必须写成 `[fallback."睡眠"]`。

### 生成结果 `data/schedule.db`（SQLite，永久归档）

**第一轮**（主生成，一段一次调用）：`story` / `manner` / `mood` / `busy`。
**第二轮**（话题提炼，全天一次调用，用便宜模型）：`topic` / `topic_keys`。
删掉数据库就退回纯手写的底稿状态，任何时候都能回滚——**LLM 绝不回写骨架**。

运行期的热路径（每轮 planner / replyer 注入）读的是内存副本（最近 3 天），
数据库只在批次结束时写、启动时读一次，所以用同步 `sqlite3` 是安全的。

#### 加列要走迁移，不要删库

`CREATE TABLE IF NOT EXISTS` 对**已存在**的表完全不动——加了新列不会生效，读的时候
`row["新列"]` 直接抛 `IndexError`，插件 `on_load` 失败、整个日程功能静默消失。
v3.0 → v3.1 加 `topic` 列时实际撞到过。

归档库是永久保留的，不能靠删库重建过版本。所以 `ScheduleDB.connect()` 里有一步
`_migrate()`：比对 `_EXPECTED_COLUMNS` 与实际列名，缺什么补什么。
**以后往表里加列，记得同步往 `_EXPECTED_COLUMNS` 里加一条。**

#### 表结构

`days` —— 一天一行，批次元信息

| 列 | 说明 |
|---|---|
| `date` (PK) | `YYYY-MM-DD` |
| `weekday` | 0=周一 … 6=周日 |
| `holiday` / `weather` | 生成时的节假日名与天气预报 |
| `day_digest` | 当天结束时的滚动概要 |
| `batch_reason` | 每日批次 / 冷启动补跑 / 手动触发 / 话题重提炼 |
| `batch_at` / `batch_elapsed` | 批次结束时刻（JST）与耗时（秒） |
| `ok_count` / `total_count` | 生成成功段数 / 总段数 |
| `aborted` | 非空表示整批中止，内容即原因 |

`segments` —— 一段一行，主键 `(date, slot)`

| 列 | 说明 |
|---|---|
| `date` / `slot` / `seq` | 日期、`HH:MM-HH:MM`、当天第几段 |
| `title` `place` `outfit` `company` `kind` | **骨架快照**——骨架会随换季整份替换，所以存当时的值，别指望回看时还能反查 |
| `story` `manner` `mood` `busy` | 第一轮主生成 |
| `topic` `topic_keys` | 第二轮话题提炼；`topic` 为空表示这段没什么好说的，`topic_keys` 是 JSON 数组 |
| `generated` | 0 表示这一段用的是底稿 |
| `negative_level` | 轻微 / 中等 / 空 |
| `model` / `generated_at` | 生成用的**模型名**与时刻 |

`shares` —— 谈资的分享状态，主键 `(date, slot, session_id)`

| 列 | 说明 |
|---|---|
| `injected` | 这条谈资在该会话被注入过多少次 |
| `shared_at` | 检测到她说出口的时刻；空 = 还没说 |
| `reply_text` | 判定为"说出口"的那条**回复原文** |
| `hit_key` | 触发判定的那个关键词 |

**按会话独立**：跟不同的人聊，同一件事说一遍是正常的。
**必须落库**：放内存的话重启就清零，她会把今天已经说过的事再说一遍。

`reply_text` / `hit_key` 判定逻辑一个都不用（判定只需要"说没说过"这一个比特），
所以它们只落库、不进内存缓存。加这两列是因为**光看「已说出口」判断不了检测准不准**：
她可能根本没提这件事，只是恰好用到了同一个词。它们只在"检测到说出口"那一次带值，
注入时是空串，所以 upsert 写成「给了才覆盖」，否则之后的注入会把原文冲掉。

#### 重新生成必须清掉分享状态

**分享状态是绑在那条 `topic` 上的，可这张表按 `(date, slot, session_id)` 建键，换了 topic 键还是同一个。**
所以一段被重新生成之后必须把它的 share 行整个删掉，否则 `is_shared` 会拿上一版的"说过了"
把新谈资一直摁住——一次都注入不出去，**不报错、不进日志**。

实机踩到过：某段 19:02 说出口，20:54 整天重跑换了新 topic，新 topic 从此再没被注入。
是 viewer 上那行「已说出口 19:02」还挂在一条明显不是它的 topic 底下才暴露出来的。

清除走 `ScheduleStore.reset_shares()`，调用点两处：`run_batch` 每段写入新 state 之后，
以及 `/status topics` 重提炼之后。注入计数一并清零——它记的是上一版 topic 的次数。

### 自带浏览器

```bash
uv run python plugins/04_a_day_with_mittes/viewer.py           # 只有本机能开
uv run python plugins/04_a_day_with_mittes/viewer.py --lan     # 局域网内可开，启动时打印地址
uv run python plugins/04_a_day_with_mittes/viewer.py --lan --port 9000
```

只用标准库、只读方式开库，不会跟运行中的 bot 抢写锁。
左侧按日期列表，右侧是当天十段的完整内容（故事、心情、忙碌度、说话方式），外加每段的
话题、关键词、分享状态和说出口时的回复原文。底稿段和负面事件段各有角标。

**「现在」一律按 JST 判定**，跟打开页面的人在哪个时区无关；打开时默认落在 JST 的今天，
并自动把当前时段滚到视口中央（一天十段拉得很长，22:30 那段否则要滚到最底下）。

> 早期版本这里错得更隐蔽：日期取 `toISOString()`（UTC）、时刻取 `getHours()`（浏览器本地），
> 两个时区混着用——即使在 JST 机器上，00:00~09:00 之间高亮也会跑到隔壁那天去。

> `--lan` 监听 `0.0.0.0` 且**没有任何鉴权**——同一局域网里知道地址的人都能看到
> 全部日程内容。自用工具的取舍，别往公网做端口映射。

## 运行

**每天 12:00（JST）批量生成次日全部 10 段。** 批量指的是时机，不是把十段塞进一次调用：
批次内部仍然一段一次调用、顺序执行，前一段的结果喂给后一段。

- 生成的是**次日**：12:00 才生成当天的话，00:00~12:00 那几段早就过去了
- 主生成跑完后，再用便宜模型跑**一次**话题提炼，全天十段一起出
- 天气用**预报**而非实时——提前一天生成拿不到实时天气
- 冷启动时**今天和明天缺哪天补哪天**，期间用底稿顶着，**不阻塞回复链路**
- 结果（成功和失败）报到配置的日志群，静默成功等于没有监控

**提前生成好的日子不会被重跑**：每日批次先查「明天有没有记录」，有就跳过。
所以手动生成一整周之后，接下来七天的 12:00 批次都会跳过，直到第八天才真正开跑。
注意判据是**有没有记录**而不是**生成成功没有**（这是为了防止模型挂掉时反复重启空转一整轮），
所以提前生成的某天如果十段全退回了底稿，它同样会被跳过，得手动补。

### 负面事件

心情默认正向，但一条平坦的正向曲线同样假。所以负面情绪不靠"随机变差"制造，
而是每周随机安排 N 次（默认 2）"不顺心的事"，再让心情跟着这件事走。

**排期只决定"何时、多重"，"是什么"由生成时的 LLM 依骨架现编**——不写事件池，
写死清单等于把她这辈子会遇到的倒霉事限定成那十几种（这正是原则一的第一次应用）。
强度只有轻微/中等两档，没有"重大"：重大事件要影响好几天，而承接链只覆盖相邻一两段。

排期结果落在 `data/negative_schedule.json`，可以直接看、直接改。

| `/status batch [日期\|today]` | 立即跑一次批次，默认次日 |
| `/status topic` | 当前时段的话题、关键词、各会话的分享状态 |
| `/status topics [日期]` | 重跑话题提炼，默认今天 |

`/status prompt` 最要紧——它直接验证注入位置对不对，省得去翻 `logs/maisaka_prompt` 的 dump。

耗时的几条（`batch` / `regen` / `next` / `topics`）走后台派发后立刻返回：
`plugin.invoke_command` 的 RPC 超时是 60 秒，而一整批要好几分钟，同步做完必然超时。

> **批次跑起来之后不要动插件目录里的任何文件。** 主程序对插件目录有文件监听热重载，
> 改一个字就等于重载插件，后台跑着的批次会跟着协程一起消失，而且**一行日志都不会留**。
> 重启 bot 同理。这个坑踩过两次。

## 可观测性

每次 LLM 调用都落盘到 WebUI 推理过程页，分类 `a_day_with_mittes`、会话 `schedule_batch`。
三种调用靠 `request.kind` 区分：`schedule_segment`（时段生成）、`schedule_digest`（当日概要）、`schedule_topics`（话题提炼）。

WebUI 那个页面**没有上报接口**，就是在扫 `logs/maisaka_prompt/` 目录树，payload 格式
（`schema_version: 6`）写死在主程序里。所以 `preview.py` 自带一份拼装代码。

> **这是隐形耦合点**：上游改了字段名，这里写出的文件会被静默忽略——页面空着且不报错。
> 同步主程序版本时要主动来查，详见工作区的 `doc/插件适配记录/`。

## 换季提醒

当前骨架覆盖的是**日本的暑假**，全周没有 `kind = "上学"` 的时段。
开学后需要另写一套学期骨架（周一至周五白天替换为上学 + 通学，店里的班次相应往后压），
