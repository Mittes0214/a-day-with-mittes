# Mittes 的一天 (A Day With Mittes)

给一个 MaiBot 角色一份会自己长出来的日程，并让它以**不被复述**的方式影响她说话。

当前 v3.1.5。

> **这是一个自用插件，不是通用组件。** 角色设定、时区（JST）、一周的时段骨架、
> 模型任务名都是硬编码或写在配置里的，直接装到别的部署上不会开箱可用。
> 公开出来是因为其中两部分可能有参考价值：
> **三通道的注入设计**（下一节）和**写生成类 prompt 的两条原则**（再下一节）。

---

## 要解决的问题

把日程做成"一句话查表"再喂进上下文，角色会反复提起它——
"我现在正在洗碗呢，有什么事情吗？"。在 prompt 里写"不要提及"没有用，
那是在跟注意力机制对着干。

问题不在"用注入还是用工具"，而在于传进去的是**事实**还是**风格**：

| | 内容 | 出现时机 | 是否含活动名词 |
|---|---|---|---|
| **事实层** | 她具体在做什么（故事化文本） | 只有被问才出现（Tool） | 有，这是它的价值 |
| **状态层** | 她的身体/情绪，以及这如何影响说话 | 每轮都在（常驻注入） | **绝对没有** |
| **谈资层** | 这段时间里值得说给人听的那一件事 | 常驻注入，**说出口后立刻撤掉** | 有——唯一的例外 |

「正在洗碗」是一句可陈述的事实，模型有复述冲动；「你有点累、话短」不是可陈述内容，
模型没法复述它，只能照做。**状态层的不可复述性完全建立在「没有活动名词」这条纪律上**，
所以 `manner` / `mood` / `busy` 三个字段在落盘前都要过一遍禁名词校验。

谈资层是有意开的口子。事实层有个先天缺陷：几乎没人会主动问「你在干嘛」，
工具不被调用，写得再好的 story 也永远用不上。谈资层给她一个主动出口，
而它防复读的方式和状态层不同——**说完就从上下文里消失**，一件事只说一次。

## 写 prompt 的两条原则

这部分是这个插件里最可迁移的东西。两条原则都有实测数据支撑，
数字来自同一份生成结果（20 个时段，两天）。

### 原则一：规则只能「排除」，不能「示范」

**禁令**排除掉一部分输出，剩下的仍然是无限的——「不要写重大事件」之后，小事还有无穷种写法。
**示范**（列一串题材、给几个措辞、配一个完整例句）会让模型在示范附近采样，
创作自由度当场坍缩。

| prompt 里写了什么 | 实测结果 |
|---|---|
| 配置里手写一份"倒霉事"清单 | 事件种类被限定在清单内，几周就开始重复 |
| 给「首句要出现角色名」配了一个完整例句 | 20 段里 13 段用同一个开头，其中一整天 10 段全是它 |
| 「打翻一杯水、找不到发圈、被熟客认出来……」 | 这些题材词在 20 段里命中 5 段 |
| 「踏实 / 懒洋洋 / 心里冒泡 / 跃跃欲试 / 被逗乐」 | 这些措辞在 20 段里命中 9 段，其中一条被**逐字**照抄 |

**"安全的正例"很可能根本不存在。** 一度以为"示范结构判据的对照例是安全的"，
依据是某个正例"20 段零照抄"——但那个统计只看了题材。一个完整例句同时携带三层：

| 层 | 例句里是什么 | 被复制了吗 |
|---|---|---|
| 题材 | 蛋包饭、画小熊、四号桌 | 否，0/20 |
| 句式 | 逗号连缀，每句 3 个逗号 | **是**，生成结果平均每句 2.8 个逗号 |
| 文体 | 间接引语 + 一句抒情收束 | **是**，10 段里 0 处直接引语、7 段以抒情句收尾 |

文体是最难察觉的一层，因为它不像题材那样显眼——它看起来只是"写得好"。

落笔时：**反例可以留，正例要吝啬**。✗ 是排除，✓ 是种子，只在"没有正例就说不清这条判据"时给一个。
**不列题材清单**，正向反向都不行——反向清单（「睡觉、洗澡、发呆、赶路就留空」）
会替模型做完判断，实测把「画油画」「涂指甲油」这些其实很有得讲的段落顺手扫掉了。

### 原则二：只写模型不可能知道的信息，不写它本来就会的能力

按原则一整理之后，story 的规则一度变成这样——全是禁令，符合原则一，但**依然是错的**：

```
- 长短句交错。一整段用逗号把动作串下来，读的人喘不过气
- 有人说话就写成引号里的原话，不要一律转成「说是……」
- 别每段都收在一句总结性的抒情上
```

一个称职的写手第一次读到「长短句交错」只会觉得莫名其妙。
这类规则是在**治症状**——真正的病因是另一条约束：「100~150 字 + 有起因有推进有转折」。
130 字塞完整三幕，只能靠逗号把动作串起来。把字数放开、把任务说清楚，句法自己就顺了。

| 留 —— 它不可能知道 | 删 —— 它本来就会 |
|---|---|
| 人称/格式契约（下游字段要对齐） | 长短句、对话怎么写、别都收在抒情上 |
| 字数预算 | 「有起因、有推进、有一点小转折」 |
| 外部事实（地点 / 服装 / 同处） | 「不是定格一帧画面」 |
| 跨调用状态（它看不到全局） | 「把它写成这段时间的主线」 |
| 常驻注入的禁名词纪律（设计地基） | |

按这把尺子，story 的规则从 20 行降到 4 行。另外两类规则值得定期清查：

- **死规则**——指向已经不存在的东西。`manner` 里曾有一条「不要写篇幅要求，那是另一个字段的事」，
  而那个字段早就整个取消了。
- **执行不了的规则**——`mood` 里曾有「不要一整天都在同一个强度上」，
  但时段是**一段一次调用**，模型只看得到上一段，看不到"一整天"。
  换成它确实看得到的参照（「和上一个时段拉开一点」）才有意义。

## 接入方式

| 类型 | 名称 | 说明 |
|---|---|---|
| Tool | `get_current_schedule` | 事实层：返回当前时段的故事化文本，被问才吐 |
| Tool | `get_weather` | 查询指定城市的实时天气和近 3 天预报 |
| Hook | `maisaka.planner.before_request` | 在「时间：」那条 item 后插入状态层（忙碌度 / 心情） |
| Hook | `maisaka.replyer.before_model_request` | 在 `reply_reference` 之前插入说话方式与谈资 |
| Hook | `maisaka.replyer.after_response` | `observe` 模式只读，检测谈资有没有被说出口 |
| Command | `/status *` | 调试命令，仅 operator |

注入全部走插件 hook，没有修改主程序源码。但有**两处直接 import 主程序内部模块**，
不走 SDK，上游重构会打断，同步版本时要重点回归：

- `LLMServiceClient` + `LLMGenerationOptions`（`generator.py`）——为了钉死具体模型。
- `schema_version: 6` 的推理记录格式（`preview.py`）——为了让调用出现在 WebUI 的推理过程页。

## 数据

### 骨架 `schedule_skeleton.toml`（手写，纳入版本库）

7 天 × 10 段变长时段，每段七个字段：

```toml
[[schedule_mon]]
start   = "18:00"
end     = "21:00"
title   = "晚班营业"
place   = "店里营业区"          # 素材支点
outfit  = "猫耳女仆装"          # 素材支点
company = "客人、店长"          # 素材支点
kind    = "工作"                # 唯一一个机器要读的字段
```

划界原则：**骨架放「客观且不该每天变的事实」，LLM 写「这些事实今天具体表现成什么样」。**
LLM 绝不回写骨架，所以删掉数据库就退回纯手写状态，任何时候都能回滚。

同一份文件里的 `[fallback."<kind>"]` 是底稿——冷启动、生成失败、缓存缺失时顶上的默认状态。

> TOML 的裸键不允许非 ASCII，中文 `kind` 必须写成 `[fallback."睡眠"]`。

### 归档库 `data/schedule.db`（SQLite，永久保留）

**第一轮**（主生成，一段一次调用）：`story` / `manner` / `mood` / `busy`。
**第二轮**（话题提炼，全天一次调用，用便宜模型）：`topic` / `topic_keys`。

运行期的热路径（每轮 planner / replyer 注入）读的是内存副本（最近 3 天），
数据库只在批次结束时写、启动时读一次，所以用同步 `sqlite3` 是安全的。

`days` —— 一天一行，批次元信息

| 列 | 说明 |
|---|---|
| `date` (PK) | `YYYY-MM-DD` |
| `weekday` | 0=周一 … 6=周日 |
| `holiday` / `weather` | 生成时的节假日名与天气预报 |
| `day_digest` | 当天结束时的滚动概要 |
| `batch_reason` | 每日批次 / 冷启动补跑 / 手动触发 / 话题重提炼 |
| `batch_at` / `batch_elapsed` | 批次结束时刻（JST）与耗时（秒） |
| `ok_count` / `total_count` | 生成成功段数 / 总段数 |
| `aborted` | 非空表示整批中止，内容即原因 |

`segments` —— 一段一行，主键 `(date, slot)`

| 列 | 说明 |
|---|---|
| `date` / `slot` / `seq` | 日期、`HH:MM-HH:MM`、当天第几段 |
| `title` `place` `outfit` `company` `kind` | **骨架快照**——骨架会随换季整份替换，所以存当时的值 |
| `story` `manner` `mood` `busy` | 第一轮主生成 |
| `topic` `topic_keys` | 第二轮话题提炼；`topic` 为空表示这段没什么好说的，`topic_keys` 是 JSON 数组 |
| `generated` | 0 表示这一段用的是底稿 |
| `negative_level` | 轻微 / 中等 / 空 |
| `model` / `generated_at` | 生成用的模型名与时刻 |

`shares` —— 谈资的分享状态，主键 `(date, slot, session_id)`

| 列 | 说明 |
|---|---|
| `injected` | 这条谈资在该会话被注入过多少次 |
| `shared_at` | 检测到她说出口的时刻；空 = 还没说 |
| `reply_text` | 判定为"说出口"的那条回复原文 |
| `hit_key` | 触发判定的那个关键词 |

按会话独立计数：跟不同的人聊，同一件事说一遍是正常的。

## 运行

**每天 12:00（JST）批量生成次日全部 10 段。** 批量指的是时机，不是把十段塞进一次调用：
批次内部仍然一段一次调用、顺序执行，前一段的结果喂给后一段。

- 生成的是**次日**：12:00 才生成当天的话，00:00~12:00 那几段早就过去了
- 主生成跑完后，再用便宜模型跑一次话题提炼，全天十段一起出
- 天气用**预报**而非实时——提前一天生成拿不到实时天气
- 冷启动时今天和明天缺哪天补哪天，期间用底稿顶着，不阻塞回复链路
- 结果（成功和失败）都报到配置的日志群

### 负面事件

心情默认正向，但一条平坦的正向曲线同样假。所以负面情绪不靠"随机变差"制造，
而是每周随机安排 N 次（默认 2）"不顺心的事"，再让心情跟着这件事走。

**排期只决定"何时、多重"，"是什么"由生成时的 LLM 依骨架现编。**
强度只有轻微 / 中等两档，没有"重大"：重大事件要影响好几天，
而承接链只覆盖相邻一两段，扛不住跨天的情绪线。

排期结果落在 `data/negative_schedule.json`，可以直接看、直接改。

## 调试命令

| 命令 | 作用 |
|---|---|
| `/status` | 当前时段的各字段、时段边界 |
| `/status prompt` | 本时段实际注入 planner / replyer 的**原文** |
| `/status day` | 今天各段的骨架 + 生成状态 + 负面事件标记 |
| `/status db` | 归档库覆盖范围、段数、文件大小 |
| `/status regen` | 强制重生成当前时段，新旧并排 |
| `/status next` | 提前生成下一段但不切换 |
| `/status neg` | 本周负面事件排期 |
| `/status neg reroll` | 重摇本周排期 |
| `/status neg clear` | 清空本周排期 |
| `/status neg add <日期> <时段> [轻微\|中等]` | 手动指定一条 |
| `/status batch [日期\|today]` | 立即跑一次批次，默认次日 |
| `/status topic` | 当前时段的话题、关键词、各会话的分享状态 |
| `/status topics [日期]` | 重跑话题提炼，默认今天 |

`/status prompt` 最要紧——它直接验证注入位置对不对，省得去翻 `logs/maisaka_prompt` 的 dump。

耗时的几条（`batch` / `regen` / `next` / `topics`）走后台派发后立刻返回：
`plugin.invoke_command` 的 RPC 超时是 60 秒，而一整批要好几分钟，同步做完必然超时。

## 常见问题

### 为什么谈资是"说完撤掉"，而不是注入"这件事已经说过了，别再提"？

因为要否定一件事，你必须先把它写进上下文。写进去之后，
注意力对「伞的事」的反应远强于对「别提」的——结果就是更容易被提起。
不可复述只能靠**上下文里根本没有**，没有别的办法。

### 为什么模型要填模型名，不能只填任务名？

`llm.generate` 这条 capability 只收任务名（内部走 `resolve_task_name`），
而任务名只决定**候选池**。如果那个任务的 `selection_strategy` 是 `random`，
每次调用会在名单里随机挑一个模型——本部署的 `replyer` 名单有四个模型，
最强的那个只有 1/4 的概率被选中。

整套 prompt 的判据是照着强模型的水平定的，随机挑模型会让每天的质量方差
**压过 prompt 本身的影响**——那时候再去调 prompt，等于在噪声里找信号。

绕开的办法是直接用 `LLMServiceClient(task_name=...)` +
`LLMGenerationOptions(model_name=...)`，任务名只当基座，模型由 `model_name` 覆盖。

### `base_task` 为什么选 `memory`？

指定模型之后，基座任务实际只提供 `hard_timeout` 和统计管线。
本部署里 `replyer` 的 `hard_timeout` 是 60 秒、`utils` 只有 **20 秒**，
而单段生成实测出现过 36.9 秒，话题提炼更是一次吞十段 story。
`memory` 的 240 秒够宽裕，仅此而已——换个部署就该按自己的配置重新挑。

### 为什么 `max_tokens` 给到 32000？

因为推理模型的 reasoning 和正文**共用这一个预算**。
把上限设成 4000 时，出现过模型把 4000 token 全部烧在 reasoning 上、
一个字正文都没吐出来的情况，而返回状态仍是 `completed`，主程序不当失败。

上限给高不额外花钱（按实际用量计费），但能挡住这类静默截断。
代码里对空响应也分两种成因报错：「被 max_tokens 截断」和「真的空」。

### Command 的正则命名组，为什么不能写成同名形参？

因为主程序把 `(?P<day>…)` 整包塞进一个 `matched_groups` 字典，**不**拆成关键字参数。

写成 `async def cmd(self, day: str = "")` 不会报错，只是 `day` 永远是默认值。
这类失效全程静默——命令照常执行、照常返回成功，只是参数当没给过。
正确写法见 `plugin.py` 里的 `_group(kwargs, name)`。

### 往表里加列，为什么必须走迁移，不能靠删库重建？

`CREATE TABLE IF NOT EXISTS` 对**已存在**的表完全不动，加的新列不会生效。
读的时候 `row["新列"]` 直接抛 `IndexError`，插件 `on_load` 失败，
整个日程功能静默消失。

归档库是永久保留的，删库等于丢掉全部历史。所以 `ScheduleDB.connect()` 里有一步
`_migrate()`：比对 `_EXPECTED_COLUMNS` 与实际列名，缺什么补什么。
**以后加列，记得同步往 `_EXPECTED_COLUMNS` 里加一条。**

### 重新生成一段之后，为什么要清掉它的 `shares`？

因为分享状态实际是绑在那条 `topic` 上的，而这张表按 `(date, slot, session_id)` 建键——
换了 topic，键还是同一个。不清的话，`is_shared` 会拿上一版的"说过了"
把新谈资一直摁住，一次都注入不出去，而且**不报错、不进日志**。

清除走 `ScheduleStore.reset_shares()`，调用点两处：`run_batch` 每段写入新 state 之后，
以及 `/status topics` 重提炼之后。注入计数一并清零——它记的是上一版 topic 的次数。

### `reply_text` / `hit_key` 判定用不到，为什么还要存？

因为光看「已说出口」判断不了检测准不准。检测的判据是"命中任意一个关键词"，
阈值偏松是有意的（误判"说过了"只是少一次开口机会，误判"没说"是把同一件事说第二遍，
后者代价更大）。代价是可能出现她根本没提这件事、只是恰好用到了同一个词的情况。

要看出这一点，必须知道她**到底说了什么**、以及是**哪个词**触发的。
这两列只落库、不进内存缓存——判定逻辑只需要"说没说过"这一个比特。

### 为什么 viewer 要自己算 JST，不用浏览器本地时间？

因为"现在是哪一段"说的是**角色所在时区**的现在，跟看页面的人在哪无关。

顺带一提，一个更隐蔽的错法是日期取 `toISOString()`（UTC）、
时刻取 `getHours()`（浏览器本地），两个时区混着用——
这样即使在 JST 机器上打开，00:00~09:00 之间高亮也会跑到隔壁那天去。
现在两者都走 `Intl` 的 `Asia/Tokyo`。

### 提前生成了一整周，12:00 的批次还会重跑吗？

不会。每日批次先查"明天有没有记录"，有就跳过，
所以接下来七天都会跳过，直到第八天才真正开跑。

注意判据是**有没有记录**，而不是**生成成功没有**——
这是为了防止模型不可用时反复重启空转一整轮。
副作用是：提前生成的某天如果十段全退回了底稿，它同样会被跳过，得手动补。

### 批次跑起来之后，能改插件目录里的文件吗？

不能。主程序对插件目录有文件监听热重载，改一个字就等于重载插件，
后台跑着的批次会跟着协程一起消失，**一行日志都不会留**。重启 bot 同理。

耗时命令是后台派发的，命令本身早就返回"已开始"了，所以从聊天记录上看不出来它还在跑。
要确认，看日志里有没有本插件的 LLM 调用记录。

## 可观测性

每次 LLM 调用都落盘到 WebUI 推理过程页，分类 `a_day_with_mittes`、会话 `schedule_batch`。
三种调用靠 `request.kind` 区分：`schedule_segment`（时段生成）、
`schedule_digest`（当日概要）、`schedule_topics`（话题提炼）。

WebUI 那个页面没有上报接口，它是在扫 `logs/maisaka_prompt/` 目录树，
payload 格式（`schema_version: 6`）写死在主程序里，所以 `preview.py` 自带一份拼装代码。

> **这是隐形耦合点**：上游改了字段名，这里写出的文件会被静默忽略——页面空着且不报错。
> 同步主程序版本时要主动来查。

## 换季提醒

当前骨架覆盖的是**日本的暑假**，全周没有 `kind = "上学"` 的时段。
开学后需要另写一套学期骨架（周一至周五白天替换为上学 + 通学，店里的班次相应往后压），
整份替换而不是打补丁。**这件事没有触发机制，得靠人记着。**
