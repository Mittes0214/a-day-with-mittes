# Mittes 的一天 (A Day With Mittes)

MaiBot 插件。给角色一份每天自动生成的日程，让它影响她的状态和表达方式。

## 它做什么

- 每天自动生成次日全天日程，**一次调用出十来段**。一天切成十来个变长时段，
  每段有当时的故事、心情、所在地点和表达方式。写手看得见全天骨架，
  所以一件事可以跨几段发展再收，而不是十段各写各的。
- 表达方式跟着时段走，并在第三轮根据每一段的故事和心情单独生成。
  但她不会把日程内容念出来（"我现在正在洗碗呢"那种）。
- 每段挑一件值得说的小事。可以用它回应相关话题，也可以在对话松下来时独立吐槽或分享；
  不会先答完再生硬追加。换不换题由 planner 决定；说过之后 planner 和 replyer 两边
  同时不再提（`stop_after_shared` 可以只关掉 replyer 那半边，用来观察她会不会自己重复）。
  关联起来的几个群算同一个"说过"。
- 心情有起伏但不随机。每周随机安排几次"不顺心的事"，让心情跟着具体事件走。
- 能查她在哪、穿什么。穿搭工具返回对应套装的设定图，planner 与 replyer 共用原图，
  可以问此刻，也可以问她今天早些时候或明天。
- 结果永久归档进 SQLite，自带管理页，可以热编辑表达方式、按日期生成日程或重跑 topic。
- 生成失败不影响聊天。冷启动或调用失败时用手写底稿顶着，回复链路不阻塞。

顺带提供一个实时天气查询工具和日本节假日识别。

## 拍照每日额度

普通用户每个自然日最多成功收到 3 张新照片，按东京时间（Asia/Tokyo）每天零点重置。
QQ 用户 `923856490` 不受此限。用户身份从原会话中的真实请求消息读取，
同一平台同一用户在群聊和私聊共用额度，不由 planner 传入用户 ID 或管理员标记。

同一请求重复调用不会重复扣次；任务内的图片修正也不额外扣次。新任务入队时暂占一个名额，
确认发送成功后才计入当日额度；拒绝、生成失败、检查失败、发送失败或结果不明都会释放名额。
名额已满时请求不入队、不调用模型。管理端的本地预览不消耗聊天用户额度。
名额占用和释放与任务状态在同一 SQLite 写事务中完成，重启会按任务记录重建计数，
并发请求不能突破限额。

## 按需拍照与参考图

`take_mittes_photo` 根据真实用户请求、相关对话和请求时刻的日程快照设计手机取景。
planner 只看到简短功能说明；可拍判断、隐私规则、局部构图和发型处理均由工具内部完成。
不主动给日常聊天附图，不改变原有 topic 与私聊主动唤醒逻辑。

拍照工具的聊天反馈统一按 Mittes 本人拿手机现场拍照来表达。接下请求时可自然接话或准备拍摄，
不播报队列、检查进度或等待结果；实际发出照片前不描述画面或声称拍好。
发送后的上下文明确这是 Mittes 刚拍的照片；拒绝、额度用完和失败也使用日常聊天语境，技术过程保留在相机记录中。

相机按画面是否实际出现 Mittes 选择画风，部署清单为 `camera/references/references.json`
（`mittes-phone-photo-style-v6`）：

- 纯景物、食物、饮品和物件：用 01 咖啡近景作主画风基准；实际取景匹配时，从 09—14 的通学街道、露台、电车、咖啡店室内、夜间书桌、教室窗边中最多补一张，不传人物画风图。没有对应空间或只拍独立物件时不加补充。
- 有 Mittes 入镜，包括手、腿、穿搭或身体局部：以 02 为主画风，按请求最多补一张 15—17（女仆装、袜子、鞋子），不添加旧 03—06 或景物画风图。鞋子补充采用用户选定的前方版。

2026-10-28 用户确认人物主参考 02 更换为新上传的窗边坐姿图；参考源与 SHA-256 已同步更新，历史任务继续保留各自实际使用的参考副本。

摄影导演返回 `contains_mittes`，程序据此选参考和画风提示词，检查环节核对实际入镜情况。
`scene_context` 只为纯景物选择相关场景补充。补充图不提供本次事实，不复制天气、时段、实际光照、物件、布局或机位。
`clothing_context` 只为穿在身上的女仆装、袜子、鞋选择人物衣着补充，并同时加载当前衣柜图；衣着补充不覆盖实际颜色、款式或固定机位。前方角度可以用镜自拍，不要求所有衣着均直接俯拍。睡衣候选未采用，相关拍照仍按主基准和当前衣柜处理。
不为选择画风而加入身体部位；脱下的鞋、放在桌上的衣物与包不算人物。
普通景物可自然双手持机，双手留在镜头后；只有持物展示等实际动作需要时才让手入镜。
环境取景固定为完全无人物；“跟着人群”等日程或对话只提供情境，取景时避开行人，不把人群补入画面。取景、生图和提示词改写均保留此要求；成品检查发现路人、人群、远处小人、背影、剪影、倒影或身体局部即不通过，可在保留主体与空间关系的前提下移除时修正一次。
只在头发或人物轮廓自然入镜时选择一张外貌原图，相关衣物入镜时按当前 outfit 加入衣柜款式图。
人设图与衣柜图分别控制外貌、款式，不继承其中的脸、道具、姿势、排版或完整人物取景。
头部参考为用户指定的 `d9be7298-4cb1-4923-bbc8-4d4e2154c6a2.png` 原图的字节副本。

穿搭取景根据本次想分享的内容与自然机位确定，不固定角度，也不强制手或手机入镜。
物品、食物、饮品和环境自由取景，可以完整展示主体与周围环境，不套用穿搭的局部、紧裁或特写要求。
鼻子及以上面部须实际遮住或裁出，包含镜面反射和画中画；嘴、下巴及头发可以入镜，范围服从本次取景。
人物自拍可在鼻子下方裁切或按当前动作自然遮挡，不默认把整个头部裁掉；暗光或阴影不能代替实际遮挡。
生成与检查均关注正常头颈肩比例、躺姿承托关系，以及颈部异常拉长、肩线下移等明确结构错误。
生图提示词中的快照与参考图用途采用文字排版，不附文件名、哈希等归档元数据；完整快照仍供取景和检查使用。
生图文字快照省略所属日程日期、时段位置安排及道具设定，保留拍摄时间、当前地点、穿搭、外貌和时段故事。
日常发型以双马尾为主，女仆装扎牢；冰场、浴后等活动采用当前衣柜及日程允许的整理方式。
照片检查同时拿到实际使用的参考图，分别核对画风、外貌、款式与镜头关系。
每次取景、生图、检查及必要的改写或修复调用，均在任务的 `model_calls` 中归档实际系统提示词、输入文本、附图顺序、返回结果与错误；不保存认证信息。

可见头发的头颈肩关系、重力和遮挡在初稿中处理。初稿检查合格便直接交付，不为头发固定生成第二版。
只有检查发现明确且可修复的问题时，才按原有流程修正一次并复检；不可修复或修正版仍不合格时不发送。

为了维护他人隐私，不接受拍摄 Mittes 自己以外的人物，背影、身体局部或不露脸也一样。
Mittes 还是高中生，为保护个人隐私，明确要求露出鼻子及以上面部或完整正脸的请求拒绝（`self_privacy`）；
拍摄头发或发型可以接受。
“店长做的蛋糕”等独立物品不因提到人物就拒绝。游戏/屏幕内容、不可见对象或指代不明的请求
也在生图前处理。不可拍时保存 `declined` 结果并回填 planner，指导 replyer 自然说明原因，
不谎称生成失败、不编造已经征求过本人意见、不自动重试或生成替代照片。
管理面板的相机页将“不可拍摄”与“生成失败”“生成成功”分开记录。

生图接口明确因内容安全拒绝时，由 LLM 复核原始需求、当前事实和参考图。仅对适宜的普通生活照整理场景表述，并在同一任务内重试一次；不改年龄、身份、穿搭、场景或参考图，不对不适宜请求改写重试。
重试后的成品仍走原来的图片检查。再次被拒绝、复核不允许或复核结果无效时停止；超时、网关错误等生成结果不明的情况不触发提示词改写。
这一次复核重试与后续成品修正共用任务上限，不额外扣拍照额度。拦截原因、被拒提示词、改写结果与用量归档在相机记录中。

## 安装

1. 把整个目录放进 MaiBot 的 `plugins/` 下。
2. 复制 `config.example.toml` 为 `config.toml`，按下面说明改。
3. 重启 MaiBot。

首次启动会自动补生成今天和明天的日程，期间用底稿顶着。

## 配置

```toml
[generation]
run_at          = "12:00"             # 每天几点跑批次，生成的是次日全天
model           = "claude-sonnet-5"   # 全天生成
topic_model     = "claude-sonnet-5"   # 第二轮抽取
expression_model = "claude-sonnet-5"  # 第三轮表达方式
base_task       = "memory"             # 基座任务，见下
temperature     = 0.9

negative_event_quota  = 2          # 每周安排几次"不顺心的事"
negative_medium_ratio = 0.3        # 其中判为"中等"强度的比例

[manner]
enabled          = false            # 表达方式（replyer 的 A 块）总开关。
                                    # 关掉后第三轮不生成、replyer 不注入、管理页不显示；
                                    # 库里已有的 manner 原样保留，改回 true 就恢复

[topic]
enabled          = true             # 谈资总开关，关掉后两条通道都不注入、工具也不暴露
stop_after_shared = true            # false：用掉之后仍然每轮注入
linked_groups    = []               # 例 [["1016077305","1059037995"]]：组内任一群说过就都算说过
linked_platform  = "qq"

[topic.reply_channel]               # 通道一：接话（常驻，只准接话不准转话题）
enabled = true

[topic.pitch_channel]               # 通道二：开口（get_mittes_topic，只在窗口期暴露）
enabled            = true
fresh_minutes      = 30             # 新鲜期：时段开始后 30 分钟内
breakpoint_minutes = 60             # 断点期：从"下班/睡醒"起最多 60 分钟
busy_kinds         = ["睡眠","工作","上学"]
idle_kinds         = ["自由","外出","通勤"]
lookback_minutes   = 10             # 「对方正在回应她」往回看多久
max_pitches        = 3              # 每段每会话最多被取材几次

[observability]
report_group_id  = ""              # 批次结果报到哪个群，留空则不报
report_platform  = "qq"
weather_location = "Tokyo"         # 生成时查天气预报用的地名

[components]
enable_get_mittes_schedule = true  # 关掉的 Tool 不会出现在 LLM 的工具列表里
enable_get_mittes_outfit   = true
enable_get_mittes_topic    = true
enable_get_weather         = true
```

三个 `*_model` 填的是 `model_config.toml` 里 `[[models]].name` 的模型名，不是任务名。
`base_task` 填任务名，只用来借它的 `hard_timeout`，挑一个超时够宽的
（全天生成实测 147~195 秒，240 秒只剩两成余量）。原因见 [DESIGN.md](DESIGN.md)。

## 目录

| 目录 | 内容 |
|---|---|
| `generation/` | 三阶段 LLM 生成管线、prompt 加载器与完整 prompt |
| `schedule/` | 日程骨架、内存状态、SQLite 归档、节假日和负面事件排期 |
| `character/` | 衣柜查询代码与衣柜资产 |
| `weather/` | 实时天气和预报查询 |
| `observability/` | WebUI 推理过程记录 |
| `frontend/` | 日程归档与管理页面 |
| `data/` | 数据库、节假日缓存等运行时数据，不进版本库 |

手写资产包括 `schedule/skeleton.toml`、`character/wardrobe.toml`、
`character/outfit_images.toml` 和
`generation/prompts/*.prompt`。prompt 一次请求使用一个完整文件，改配方不用碰 Python。

骨架的 `outfit` 填的是衣柜里的套装名。名字进 prompt 给 story 用，
服装细节保存在衣柜并展示在 mittes-panel 的衣柜页，穿搭工具只返回设定图。两种粒度为什么分开，见 [DESIGN.md](DESIGN.md)。

`get_mittes_outfit` 按查询时刻选择套装，成功结果只有 `【Mittes 的服饰参考资料】`。
插件在 planner 请求前，于成功查询的结果之后单独补一条 `user` 多模态资料；
在 replyer 请求前，于 `reply_reference` 之前补入相同图片。资料内容只有标题和原图，
不追加服装清单、时间或套装名。

图片仅存在于模型请求，不通过 `content_items` 返回，不注册 `tool_result:…` 媒体索引，
也不作为可转发的图片写入聊天历史。服饰工具不提供发送或转发设定图的功能，从来源上去掉
转发通道，不靠发送前取消消息，以免 planner 误以为发送失败而反复尝试。

图片关联使用主程序的逻辑轮次 ID 和工具调用 ID，全部在插件内部完成。
同一轮查询多个时刻时按顺序保留不同套装；跨轮、跨会话不沿用，失败的查询不注入。
replyer 第一次请求固定图片名单，重试保持不变。replyer 实际选中的模型必须支持视觉；
非视觉模型会跳过图片并记录警告，不退回文字清单。planner 沿用主程序的视觉模型配置。

换季时同步更新 `outfit_images.toml` 和图片文件，映射必须覆盖衣柜中的全部套装。
图片首次读取和编码在线程中完成，随后缓存；替换图片后重启插件以刷新缓存。

回归检查（在 MaiBot 根目录运行，不请求模型）：
`uv run python -m pytest plugins/01_a_day_with_mittes/tests/test_outfit_images.py -q`。

一天从凌晨 02:00 算起，跨零点那段写成 `24:00-26:00`，归属当天。

骨架一共九张表：周一到周日各一张，外加两张祝日表。**哪天用哪张不由星期几决定**——
日本的法定祝日学校放假，按周中骨架排会让她在法定假日的白天照旧"在上课"
（`上学` 是机器读的 busy kind，那几段她不会主动开话头）。祝日落在店定休日（周一）
走全休表，否则走全天班表；校历上那些不是祝日又改变整天形状的日子
（文化祭、考试周）写进 `skeleton.toml` 末尾的 `[calendar.override]`。
"今天是连休第几天、明天还用不用上学"不写进骨架，生成当天现算后注进 prompt。

LLM 只负责写"这些事实今天具体表现成什么样"，绝不回写骨架。
换季或换角色时，**骨架和衣柜这两份**整份替换、不打补丁——它们是配套的，
骨架的 `outfit` 填的是衣柜里的名字，只换一边会对不上。prompt 不跟着换季走。

## 命令

仅 operator 可用。

| 命令 | 作用 |
|---|---|
| `/status` | 当前时段的各字段、所在地点、时段边界 |
| `/status day` | 今天各段的骨架 + 生成状态 |
| `/status prompt` | 本时段实际注入的原文 |
| `/status topic` | 当前时段的话题、用掉没有、取材次数、谈资工具露不露 |
| `/status db` | 归档库覆盖范围、段数、文件大小 |
| `/status batch [日期\|today]` | 立即跑一次批次，默认次日 |
| `/status topics [日期]` | 只重跑第二轮（地点时段轴 + 话题） |
| `/status neg` | 本周"不顺心的事"排期 |
| `/status neg reroll` / `clear` | 重摇 / 清空本周排期 |
| `/status neg add <日期> <时段> [轻微\|中等]` | 手动指定一条 |

`/status prompt` 最常用，直接看到注入了什么、注在哪，不用去翻日志。

耗时的几条（`batch` / `topics`）会立刻返回"已在后台开始"，跑完再报结果。
**跑的期间不要改插件目录里的文件，也不要重启**：主程序有文件监听热重载，
会把后台批次连协程一起带走，且不留日志。

## 查看与管理日程

```bash
python frontend/viewer.py                    # 只有本机能开
python frontend/viewer.py --lan              # 局域网内可开，启动时打印地址
python frontend/viewer.py --lan --port 9000
```

纯标准库，不需要装依赖，也不需要 bot 的虚拟环境。左侧可以指定日期生成日程；
选中一天后可以重新生成当日日程、重新生成 topic，或只重跑当日全部表达方式。每段的表达方式都可直接编辑，
保存后由运行中的插件同步更新内存和归档，不用重启 bot。打开时自动定位到当前时段。

当日穿搭以设定图横向展示，相同搭配只显示一次，此刻穿着的搭配排在最前并标记；
点击图片或日程中的穿搭名，可以放大查看和打开原图。
整个衣柜（全部搭配、历史版本、映射与骨架引用的一致性检查）不在这里，
在 mittes-panel 的「衣柜」页（`/wardrobe`，只读）单独维护。
外搭与模型参考资料共用 `character/outfit_images.toml`，独立内搭使用 `character/innerwear_images.toml`。
没有设定图的临时搭配明确标注；图片按需加载，更新图片后刷新即可看到新版本。

服饰生图先读 [固定画风规范](character/art-direction/STYLE.md)，再使用提示词生成脚本。
规范、两张固定参考图、SHA-256 校验和提示词模板均随插件保存；新图不得自动替换基准。
[当前外搭图集](character/design-sheets/2026-10-12/outerwear-v6/README.md)保留原始提示词和衣柜快照。

> `--lan` 监听 `0.0.0.0` 且**没有鉴权**，同一局域网内知道地址的人不但能看到内容，
> 也能编辑表达方式和触发生成。别往公网做端口映射。

- **祝日和连休铺底色**，连休整段连成一条带子（中间的格子不留圆角，跨周就断在行尾）。
  只给祝日铺底色是不够的——凑成连休的那两天周末看着还是普通周末，一眼分不出这是五连休。
  普通的两天周末不铺，不然满屏都是底色，连休反而不显眼了。
- **有归档的日子下面有个点**，点一下直接跳过去；当前正在看的那天高亮，今天描细框。
- 下面列出**本月祝日**和**连休**（连着三天以上的非工作日才算，两天的普通周末不列）。
- 每个祝日下面有一句中文说明，连休下面写清楚是哪几天凑出来的（周末还是哪个祝日），
  黄金周 / 白银周额外挂个牌子。
- 日本没有调休补班，所以不存在"周末被征用去上班"这种格子。祝日撞上周日，补休顺延到
  之后头一个平日（振替休日，标"顺延"）；两个祝日中间夹的那天也放（国民の休日，标"夹日"）。
  这两种在 holidays-jp 的数据里本来就是独立条目，直接照着标。
- 页面的滚动条跟着主题走。浏览器默认那条在深色下是亮白的，比页面里任何内容都抢眼。

祝日表走 `/api/holidays?year=`：先读插件下好的缓存（`data/plugins/<插件ID>/holidays/JP/<年>.json`），
没有就由 viewer 自己去 holidays-jp 下一份写进同一个文件——插件只在生成那一年的日程时才下，
而日历可以被翻到任意一年。取不到时日历照常画，只是那一年没有祝日标记，页面上会写明。
**这是 viewer 唯一一处对外网发的请求。**

> 窄于 1240px 时日历自动收起（`aside` 238 + 正文 900 已经占满），
> 手机那档（≤640px）改成堆在正文下面。

## 归档库

`data/schedule.db`，SQLite，永久保留。四张表：

| 表 | 一行是什么 |
|---|---|
| `days` | 一天，存批次元信息（天气、节假日、耗时、脉络） |
| `segments` | 一个时段，存骨架快照 + 生成出来的 story / manner / mood / places / topic |
| `shares` | 某条话题在某个会话的状态：注入过几次、被取材过几次、有没有被用掉 |
| `admin_jobs` | 管理页递交给运行中插件的编辑与生成任务 |

删掉数据库就退回纯手写的底稿状态。库开了 WAL；只做外部查询时请用只读方式打开：

```python
con = sqlite3.connect("file:.../data/schedule.db?mode=ro", uri=True)
```

往表里加列时要同步往 `schedule/db.py` 的 `_EXPECTED_COLUMNS` 加一条。
不能靠删库重建，`CREATE TABLE IF NOT EXISTS` 对已存在的表不做任何改动。

## 私聊主动聊天

```toml
[proactive_private]
enabled = true
users = ["qq:923856490"]
```

每 15 秒检查当前日程。有非空 topic 的时段到点后，向名单用户的私聊 planner
递交一次日程事件，包含该时段的 topic。planner 根据聊天上下文和对方最近的反应
决定是否调用 `reply`；选择回复时，通过 `reply_reference` 把选中的素材交给 replyer。
不会强制发送消息，也不会自动生成照片。

原有 topic 生成、replyer 注入、群聊关联和分享检测保持原样。
新开关独立于 `[topic]` 的两条注入通道；原来的谈资工具无需开启。
需要 SDK 2.12.0，以及 `chat.open_session`、`maisaka.proactive.trigger` 权限。

每个逻辑日、时段、名单用户最多尝试唤醒一次，与是否真正回复分开记录。
记录保存在插件数据目录的 `private_topic_wakes.db`，不修改 `schedule.db` 的分享状态。
`queued` 只表示主程序接受了唤醒；`failed` 表示调用失败；`claimed` 表示已开始尝试，
可能在取消、超时或进程中断时未取得最终结果。为避免重复打扰，这些情况都不自动重试。
插件启动或重载时不补发已开始的时段；日程按日本时间和原有逻辑日规则运行。
管理员也可通过管理任务 `wake_private_topic` 手动检查当前时段，任务的
`target_date` 和 `slot` 必须与当前逻辑日及时段一致。该操作允许处理启动时跳过的
当前时段，仍只使用配置名单，仍遵守每用户每时段最多尝试一次的去重规则。
需要明确重复测试时，该管理任务可携带 `payload={"repeat":true}`，仅本次任务允许
重复唤醒并更新该时段的尝试结果；自动轮询和默认手动任务仍然去重。
对比测试还可显式指定 `source_slot`，复用今天已开始的某个时段的 topic；
任务本身的日期及时段仍必须匹配当前日程，事件保留原来的时段标注。

唤醒时将 topic 作为事件背景，交给 planner 判断联系动机及最想分享的一点。
`reply_reference` 仅同步必要事实、当前状态及核心态度，具体措辞交给 replyer。

## 按需拍照与相机记录

`take_mittes_photo(instruction, source_msg_id)` 仅在用户想看身边事物、环境或穿搭时调用，
支持根据前文展开“看看”的指代。请求先绑定真实会话和用户消息，再固定当前日程、地点和穿搭。
同一会话同一用户消息只创建一个任务；工具立即返回后台任务编号。

`[photo]` 配置启用后，经 CPA 完成取景设计、固定参考图生图和视觉检查。
生成结果遮住或裁出鼻子及以上面部，保留二次元手机随拍视角；款式参考按当前衣柜读取。
初稿检查通过便发送；明确不合格且可修复时最多修正一次，修正版仍不合格则不发送。后续近拍/微调可引用同一会话上一张已发送照片。

- 供应商通过 `api_provider` 关联主程序 `config/model_config.toml`，不复制密钥；任务不保存密钥。
- 固定参考在 `camera/references/`，来源为用户认可的场景测试图，每次验证 SHA-256。
- 归档在插件数据目录 `camera/camera.db` 与 `camera/<任务ID>/`，包括快照、方案、完整提示词、
  参考图副本、每版图片、检查结论、模型参数和阶段时间。原图默认保留。
- mittes-panel 的 `/camera` 只读展示同一份任务库和图片，不另建生成服务。
- 生成后先保存成品再向原会话发送，发送失败不重新生图；回执不明确时不盲目重发。
  成功发送的图片同步到 Maisaka 历史，并附加实际画面描述。
- 排队任务在重载后继续；进行中的生成标记中断，正在发送的任务标记待核对，不自动重做。
- 管理任务 `camera_preview` 可测试真实接口，仅保存预览，不向聊天发送图片。

默认使用 `gpt-image-2.5-sunburst`、`quality=high`；照片固定为单张竖版 2:3、`1024x1536`，
不随主体或参考图改变。接口参数与取景提示统一指定该规格，成品尺寸不符则不发送，不自动裁切或拉伸。模型和供应商需实际支持。
组件开关 `enable_take_mittes_photo` 控制工具注册，`photo.enabled` 控制调用。
